# Operations: performance, security, versioning, release

## Performance model

td is single-threaded per connection by design — one `std.Io`, `io`
passed per call, zero hidden threads and zero locks. Concurrency is
*interleaving*: the RPC client pipelines requests over one connection,
and `td.multi.Fleet` interleaves many independent connections on one
thread. Latency claims are backed by benchmarks, never asserted:

```sh
just bench            # everything
just bench multi      # fleet scaling: 100 / 1 000 / 5 000 / 10 000 sessions
just bench net        # dispatch, pipelining, socket echo, loopback RTT
```

What the suite reports, and where to read it:

- **memory/session** — live bytes through a counting allocator at each
  fleet size (`bench multi`, "build N sessions"). Flat in fleet size;
  dominated by the RPC client's fixed container slots.
- **CPU/session** — wall time of the single driving thread (`bench
  multi`, sequential roundtrips), which *is* CPU time on this model.
- **requests/sec, latency p50/p95/p99** — sequential and pipelined
  across sessions, over both an in-memory peer (includes peer crypto —
  conservative) and a real-socket anchor at 100 connections.
- **allocations** — per request and per op on every hot path.
- **event-loop utilization** — per sweep: sessions visited vs. sessions
  that delivered frames, and frames per sweep (`Sweep` in `td.multi`).

**Status of the numbers:** the measurement code is committed; the
published figures are produced by the first verified `just bench multi`
run on real hardware and belong next to it (docs intentionally do not
quote numbers that no one has run). Optimization follows the same rule:
no change ships without a before/after pair from this suite.

Sizing guidance the benchmarks are designed to answer: sweep cost is
O(live sessions); keep `tcp.read_timeout` below per-session pump
budgets on socket fleets; in-memory fleets (tests, gateways, emulators)
have no such floor.

## Security posture

- **Secrets never logged.** The handshake, session, and auth modules
  contain no logging at all; the only state renderer is redacted by
  construction; key material lives in caller-owned memory and dies with
  it. Never print a `session.State` with `{}`/`{any}` — use `{f}`.
- **Crypto is std.crypto only.** AES-256-IGE validated against OpenSSL
  KATs; SRP, DH and msg_key derivations validated against the official
  worked examples; constant-time msg_key comparison.
- **Fuzzing.** Every supported input path (TL parse/ser/de, generated
  decoders, encrypted frames, session loading, transport framing) has a
  fuzz target (`just fuzz`); hostile-input regression corpora run in
  every `just test` (`tests/compliance.zig`, `tests/fuzz.zig`).
- **Trust boundaries.** All wire input is validated before use and
  fails closed: vector counts are allocation-guarded, gzip inflation is
  bounded, malformed input never desynchronizes the session state.
- Review status: flag auth, crypto, and data-deletion changes for
  explicit review; this project treats those areas as highest-scrutiny
  diffs.

## Versioning

- The package version in `build.zig.zon` follows semver; while 0.x, the
  minor number bumps for API changes and the patch for fixes.
- The generated API layer carries the upstream schema it was generated
  from and is regenerated by `just api`; CI verifies the committed tree
  is byte-reproducible from that schema.
- The session record format (`td.session.State`) has its own version
  field with an explicit compatibility policy: unknown versions and
  unknown flag bits are rejected, never guessed at.

## Release process

```sh
just test            # full suite incl. compliance + fuzz corpora
just bench multi     # fleet sections complete at every scale
just release         # ReleaseFast cross-builds into zig-out-dist/
```

Target matrix: `x86_64-linux-gnu`, `aarch64-linux-gnu`,
`x86_64-macos-none`, `aarch64-macos-none`, `x86_64-windows-gnu`. Linux
and macOS are the supported platforms; the Windows triple builds
best-effort (blocking `std.Io` socket behavior differs) and is not a
tested platform yet.

CI (`.github/workflows/ci.yml`) runs the test suite, the API
reproducibility check, an examples smoke run and a benchmark smoke run
on every push.
