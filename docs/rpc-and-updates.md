# RPC and updates

## The client

`td.rpc.Client` drives one encrypted MTProto session over any
`td.transport.Transport`. It is single-threaded like everything in td:
`io` is passed per call, "concurrent" means pipelined.

```zig
var client = try td.rpc.Client.init(gpa, transport, &auth_key, salt, random, .{});
defer client.deinit();
try client.connect(io);
```

### One-shot and pipelined

```zig
// Typed one-shot: the request's Result decl picks the response type.
const resp = try client.invoke(io, td.api.help.getNearestDc{});
defer resp.deinit();
const country = resp.value.country;

// Explicit result type (requests without a Result decl):
const r2 = try client.call(io, req, td.api.Bool);

// Pipelined: send now, wait later — N requests share one receive pump.
const h1 = try client.send(io, req_a);
const h2 = try client.send(io, req_b);
const ra = try client.wait(io, h1); defer ra.deinit();
const rb = try client.wait(io, h2); defer rb.deinit();
```

Answers are matched by `req_msg_id`, individually or packed into one
container. A `wait` deadline expiry keeps the request registered —
retry the wait or `cancel` the handle.

### The raw path

`invokeRaw` / `sendRaw` / `waitRaw` trade generated types for control:
pre-serialized body in, owned result-object bytes out (gzip already
inflated, bounded against decompression bombs). Generic wrappers that
the generator does not emit as structs (`invokeWithLayer`,
`invokeAfterMsg`) travel this way. Free returned bytes with the
client's allocator.

### Errors

| error | meaning | recovery |
|---|---|---|
| `error.RpcError` | server answered `rpc_error` | code/message via `client.lastRpcError()` |
| `error.TimedOut` | response deadline passed | request stays registered: re-`wait` or `cancel` |
| connection errors | transport died | `connman.Manager` re-sends unanswered requests automatically |
| `error.BadResponse` | result did not decode as `T` | not retried |

`FLOOD_WAIT_X` and friends are *data*, not surprises: read
`lastRpcError()` and back off per your application policy.

#### The generated error catalog

`rpc_error` message strings are classified against a generated catalog
of 889 Telegram error ids (`td.rpc.errors_gen`, regenerated by
`just errors` from the vendored mtgo/gotd TSVs in
`tests/data/rpc_errors/`). `RpcErrorInfo` carries the classification
alongside the raw string:

```zig
const info = client.lastRpcError();
if (info.id) |id| {
    // .flood_wait_x for "FLOOD_WAIT_60"; wire(), description()
    // and parameterized() come from the catalog.
}
if (td.rpc.floodWaitSeconds(info)) |secs| { /* back off */ }
```

`classify` (`td.rpc.classifyRpcError`) maps any wire message to
`?struct { id, value }`: exact match first, then a trailing `_<digits>`
suffix is normalized to `_X` (`PHONE_MIGRATE_4` → `.phone_migrate_x`
with value 4 — the `dc.migration` parser is built on it). Unknown
messages classify as null and stay available as the raw string.

## Updates

Server-pushed API objects arrive as unknown top-level constructors
during `pump`/`wait`. The client never decodes them; it counts them
(`updates_seen`) and hands the raw TL body to your hook:

```zig
client.updates_handler = .{
    .ctx = &my_state,
    .onUpdates = myState.onUpdates, // (ctx, io, raw TL bytes) void
};
```

Contract: the body is borrowed from the frame being dispatched — decode
inside the callee, and **never re-enter the client from the handler**
(no `call`/`wait`/`pump`). Queue follow-up RPCs until the pump returns;
`td.updates.Engine.reconcile` is built for exactly that.

The updates subsystem (`td.updates`) layers on top:

- `updates.state` — pts/qts/date/seq tracking with verdicts;
- `updates.classify` — which pushed objects matter for which state;
- `updates.engine` — pure ingest plus `getDifference` reconciliation
  when a gap is detected;
- `updates.fetch` — the pump-safe hook that feeds the engine.

## Timeouts and pumps

Three clocks matter:

- `connman.Options.tcp.read_timeout` bounds each blocking read (an idle
  expiry leaves the connection usable);
- `rpc.Options.response_timeout` bounds each `wait`;
- `Manager.maintain` pings on a cadence (`ping_interval`) with a bounded
  round trip (`ping_timeout`), using `ping_delay_disconnect` as the
  keep-alive contract.

Application loops alternate `pump` (drain incoming frames within a
budget) and `maintain` (keep-alive); `connman.Manager` wraps both with
automatic repair.
